# 发布基线收敛设计

日期：2026-08-20

## 1. 背景

`codex/multi-model-cv` 工作树同时包含已提交的 V3.1 线上工作流更新器，以及尚未提交的运行时对齐、多模型实验、持久化异步任务和 Dify DSL 生成改动。当前线上 `Paper comparison V3.1` 已经通过真实 PDF/CSV 验收，但仓库源码、生成 DSL、Dify 草稿和已发布工作流之间还没有统一的发布完整性合同。

本阶段先收敛现有成果，形成可测试、可审查、可回滚的正式基线。论文解析缓存、重复数据敏感性实验、结构化指标覆盖、跨论文回归集和更广任务类型均属于后续独立阶段，不在本规格中实现。

## 2. 目标

1. 保留并审查现有全部运行时、多模型、异步任务和 Dify 生成器改动。
2. 将改动按依赖关系拆成独立、可验证、可回滚的提交。
3. 建立从 Python 源码到 Dify 已发布工作流的单一、确定性发布路径。
4. 建立只读漂移检查和可复现发布清单。
5. 在不影响当前线上 V3.1 的前提下完成全量测试和真实 PDF/CSV 验收。

## 3. 非目标

- 本阶段不增加论文 dossier 缓存。
- 本阶段不自动运行去重前后敏感性实验。
- 本阶段不改变 `metric_overrides_json` 的用户界面。
- 本阶段不扩展回归、分割或目标检测指标。
- 本阶段不清理或删除用户的临时测试目录和现场验收文件。
- 本阶段不把候选多模型工作流直接覆盖到当前线上 V3.1。

## 4. 方案选择

采用“按能力拆分正式基线”的收敛方式。

未采用的方案：

- 单次快照提交：速度快，但约五千行改动无法独立审查、定位回归或安全回滚。
- 丢弃后重新实现：历史最干净，但会浪费已经通过大量测试和现场验证的成果，并可能重新引入已解决的问题。

## 5. 架构与提交边界

依赖关系如下：

```text
运行时身份与构建摘要
        ↓
多模型实验与比较
        ↓
持久化异步任务
        ↓
Dify 工作流生成器
        ↓
发布清单与漂移检查
```

现有改动必须按以下边界审查和提交：

1. **runtime**：计算代码、依赖和构建摘要，保证实验结果能够说明实际运行版本。
2. **multimodel**：七模型套件、共享外部测试集、性能/论文接近度双排名和单模型失败隔离。
3. **async-jobs**：任务提交、查询、等待、取消、输入暂存和重启恢复。
4. **dify-generation**：由 Python 生成工作流 DSL，派生 YAML 不再作为手工逻辑来源。
5. **release-integrity**：发布清单、只读漂移检查、备份、发布后核验和受控回滚。
6. **verification**：全量测试、生成器幂等检查和真实 PDF/CSV 验收记录。

每个边界必须拥有独立 focused tests，并在提交前通过。审查现有实现时发现的行为缺陷必须先添加能够正确失败的回归测试，再做最小修复。

## 6. 单一事实来源

- 可执行工作流逻辑以 `dify/code/*.py` 和 `scripts/build_multimodel_dsl.py` 为事实来源。
- YAML 是可提交、可导入的确定性构建产物。
- 连续执行两次生成器必须产生完全相同的字节或规范化内容，第二次生成后 Git 不得出现新差异。
- V3.1 专用更新器保留兼容入口，但其通用备份、摘要、发布和核验能力逐步下沉到聚焦的发布完整性模块。
- 线上工作流不是源码事实来源；不得通过从线上复制代码来静默覆盖仓库源码。

## 7. 发布数据流

```text
Python 源码与配置
        ↓
工作流生成器
        ↓
规范化 DSL
        ↓
发布清单
        ↓
只读漂移检查
        ↓
备份旧工作流
        ↓
发布
        ↓
读取线上版本并再次核验
```

发布清单至少记录：

- Git commit；
- 工作树是否干净；
- 参与构建的源码摘要；
- DSL SHA-256；
- 工作流类型和版本；
- Dify 应用 ID；
- 草稿工作流 ID；
- 发布工作流 ID；
- 发布或核验时间；
- 回滚工作流 ID。

清单中的时间只在显式发布或现场核验时写入；纯构建清单必须能够在相同仓库状态下稳定重现。

## 8. 漂移检查

漂移检查默认只读，分别产生以下状态：

1. `source_dsl_drift`：源码生成的规范化 DSL 与仓库中的 DSL 不一致。
2. `dsl_draft_drift`：仓库 DSL 与 Dify 草稿的规范化工作流图不一致。
3. `draft_published_drift`：Dify 草稿与已发布工作流不一致。
4. `identity_mismatch`：应用、租户或工作流身份不符合显式配置。

检查结果必须包含安全错误码、差异层级和相关摘要，不输出密钥、会话令牌或完整用户文件。任何未通过显式允许的漂移都阻止自动发布。只读检查不得保存草稿、创建版本或发布工作流。

## 9. 发布、备份与回滚

- 发布前读取并验证当前草稿和已发布工作流。
- 发布前创建 Dify 可恢复工作流版本，并记录其 ID。
- 发布只接受通过生成器、测试、清单和漂移检查的候选图。
- 发布后重新读取线上图，核对节点、边、关键代码摘要和输入输出合同。
- 发布后核验失败时，报告候选发布 ID和备份 ID，并使用显式备份执行受控回滚。
- Dify 不可访问、身份不匹配或备份失败时，不允许任何线上修改。

当前线上 V3.1 在候选多模型基线完成最终验收前保持不变。

## 10. 错误处理

- **未归类工作树改动**：允许只读审查和测试；禁止生成可发布状态。
- **生成器不稳定**：测试失败，不生成可发布清单。
- **可选模型依赖缺失**：该模型标记为 `unavailable`，其他模型继续。
- **核心运行依赖缺失**：停止候选发布。
- **单模型训练失败**：套件返回 `partial` 并保留其他成功结果。
- **任务进程重启**：运行中任务转为 `needs_retry`；输入完整时允许恢复，输入损坏时返回固定错误码。
- **Dify 不可访问或身份不匹配**：不修改线上状态。
- **发布后核验失败**：不得把候选版本标记为可用，并执行受控回滚。
- **真实验收失败**：保留当前线上 V3.1。

## 11. 测试策略

### 11.1 Focused tests

- 运行时摘要对文件顺序、临时目录和平台路径分隔符稳定。
- 七个模型使用同一外部切分和 `test_digest`。
- 一个模型失败或依赖不可用时，其余模型继续并得到确定状态。
- 异步任务提交、幂等返回、进度、等待、取消和重启恢复符合合同。
- DSL 生成器覆盖默认与已支持的 LLM profile，并保持幂等。
- 发布清单的纯构建部分确定可复现。
- 漂移检查能够独立识别三层漂移和身份错误，且只读测试验证没有写操作。
- 发布后核验失败路径能够选择显式备份作为回滚目标。

### 11.2 全量回归

- 运行完整 pytest 套件。
- 不新增测试警告或资源泄漏警告。
- 连续生成 DSL 两次，第二次运行后 Git 不产生新差异。
- 不提交 `.pytest-tmp*`、`.live-artifacts` 或用户实验数据。

### 11.3 真实验收

使用当前论文 PDF 与训练 CSV 进行一次候选工作流验收，并确认：

- 工作流到达成功终态；
- 七模型成功或返回清晰的 `unavailable` / `failed` 状态；
- 所有成功模型共享同一个测试集摘要；
- 最终报告区分严格可比性与近似相似度；
- 论文 AUC `0.91` 和独立实验结果具有可追踪来源；
- 66 条重复记录警告仍然保留；
- 验收记录包含候选 commit、DSL 摘要和工作流 ID，不包含原始 CSV 行。

## 12. 验收标准

以下条件全部满足后，优先级 1 才算完成：

1. 六个提交边界均已审查并形成独立提交或有书面理由合并相邻边界。
2. 每组 focused tests 和完整测试套件均通过。
3. DSL 生成是确定且幂等的。
4. 发布清单可以从相同仓库状态重复生成。
5. 只读漂移检查能准确区分源码、草稿和已发布版本。
6. 多模型共享切分、单模型失败隔离和异步任务生命周期通过测试。
7. 当前 PDF/CSV 的候选工作流真实验收成功。
8. 当前线上 V3.1 未受到候选验收的意外修改。
9. 最终工作树不包含由本阶段新增的未提交源码或派生 DSL 变化。

## 13. 后续顺序

基线收敛完成后，按以下独立规格继续：

1. 论文 dossier 缓存与阶段复用；
2. 去重前后敏感性双跑；
3. 结构化指标覆盖体验；
4. 跨论文回归集；
5. 多模型异步链路的线上产品化；
6. 在二分类基线稳定后评估回归与分割任务扩展。
